# GoldenEye 007 (EU) web port: plan

Goal: GoldenEye 007 running in a browser (wasm, Chrome first) for a player who owns the **EU (PAL) ROM**
(SHA-1 `167c3c433dec1f1eb921736f7d53fac8cb45ee31`). The site ships **no ROM-derived data**: every
game-specific byte is read or converted from the player's ROM in the browser. Later: optional features
and online multiplayer, as in the Conker web port (`WEB_PORT_ORCHESTRATOR.md`).

Status and how-to: `docs/web/HANDOFF.md`. This file holds the decisions and the plan.

Unlike Conker, the decompilation **and** a working native PC port already exist (this repo). The work is
adapting that port to Emscripten, not writing a port layer from scratch: no difftest, no IR passes for
endianness, no relocation tables (the PC port already solved those its own way, see 1.3).

## 1. How the native PC port is built (what we start from)

### 1.1 Build
- `CMakeLists.txt` is a build parallel to the N64 `Makefile`: `src/game/*.c` + a curated `src/*.c`
  engine list + libultra audio/gu + the `port/` layer (C) + `port/fast3d/` (C++20, from the Perfect
  Dark port). GCC is preferred (the decomp's `#define inherits struct` idiom needs GCC's
  `-fms-extensions`/`-fplan9-extensions`). `ROMID` selects the region; **`REGION_DEFS` mirror the
  Makefile** (AGENTS.md non-negotiable 3).
- Region **pal-final**: `-DVERSION_EU -DLANG_EU -DREFRESH_PAL -DBUGFIX_R1 -DBUGFIX_R2 -DBYTEMATCH`,
  `-DPAL=1`, asset region `e`. Confirmed in the web build (`build-web/cmake.log`). `osTvType = OS_TV_PAL`
  (D488), the EU `video_related_8` modes give a 320x272-ish CFB (D487).
- Deps: SDL2 (window, input, audio), zlib (`port/src/rzdecomp.c` backs the game's inflate, because GE's
  own `huft` tables overflow on 64-bit, D32), OpenGL 3 via glad.
- The game sources are compiled **unmodified** except `#ifdef PORT` ABI/layout fixes (several hundred),
  mostly 32→64-bit pointer-width ones; many in `src/` are gated on `__x86_64__`.

### 1.2 Runtime model (native)
- **Memory:** an 8 MiB "N64 DRAM" arena mapped **twice** (`port/src/dram.c`): V1 at 0x70000000 (all game
  RAM: cfb, mempools; s32-safe) and a KSEG0 mirror at 0x80000000 for code that rebuilds pointers with
  `off | 0x80000000`. The ROM is mapped at the cart address 0x10000000 (`romdata.c`), followed by the
  sidecars; every ROM asset symbol is an absolute `0x10000000 + offset` (`port/src/romassets_e.s`,
  generated by `scripts/gen_romassets.py`, committed).
- **Threads:** every libultra thread is a real pthread (`port/src/libultra.c`); queues are mutex +
  condvar side tables; a tick thread posts the VI retrace at 50/60 Hz and services timers; the game's
  real `src/sched.c` runs; `osSpTaskStartGo` runs fast3d (gfx) inline or on a render worker (D481).
- **Graphics:** `port/fast3d/` = software RSP (GBI decode, transforms, lighting on the CPU) + an OpenGL
  backend (`gfx_opengl.cpp`) that already has a GLES3 path ("300 es" shaders).
- **Audio:** libaudio synthesis runs on the CPU (`src/libultra/audio`, `port/src/mixer.c`), output via
  SDL audio (`port/src/audio.c`). Audio RSP tasks just complete.
- **File IO:** `port/src/fs.c`/`system.c`: `$S/` = `data/` (ROM, sidecars, `ge007.ini`, `ge007.eep`).
- **Saves:** EEPROM 16K image in `data/ge007.eep` (`geEepromRW`).
- **Input:** SDL keyboard/mouse/gamepad → `osContGetReadData` (`port/src/input.c`, ~4k lines).
- **Pacing:** the game paces itself with `osGetCount` (`frametiming.c` busy-waits 931050 ticks per PAL
  frame); `osGetCount` scales wall time to the ~46.55 MHz counter rate (both regions).

### 1.3 Assets today
- **Committed in the tree (inherited from the decomp + upstream):** `assets/**` C files and headers
  (1408 tracked files), `scripts/filelist.{u,e,j}.csv` (ROM file offsets), `port/src/romassets_*.s`
  (symbol → ROM offset). See section 3 for the audit.
- **Extraction scripts** (`scripts/extract_baserom.u.sh`, `extract_diff.e.sh`): regenerate `assets/`
  from a ROM with MIPS binutils. "US extraction is a prerequisite" for PAL **only for this
  regeneration step**; the PC build does not need it (a clone already has what it compiles).
- **Sidecars (required to run):** three pure-stdlib Python converters (`tools_pc/d43_emit.py`,
  `d69_emit.py`, `d88_emit.py`, ~2.5k lines with `d88_propdefs.py`) turn ROM model / bg / stan / setup
  data into PC-layout (LP64, little-endian) blobs: `data/pcmodels-pal-final/` (1.3 MB) and
  `data/pccg-pal-final/` (3.6 MB), each a `.bin` + `manifest.csv`. Inputs: the ROM, `filelist.e.csv`,
  `assets/obseg/file_resource_table.inc.c` (names), and small counts parsed from
  `assets/**/ModelFileHeader.inc.c`. Releases ship them frozen (PyInstaller) and spawn them on first
  launch (`port/src/romconvert.c`). Upstream's ROADMAP already wants native C emitters (#6).
- **EU-only feasibility: yes.** G1 produced both PAL sidecar sets from the EU ROM alone in the
  container (`python3 tools_pc/d43_emit.py pal-final` etc., "ALL CHECKS PASSED"), and the web build
  boots with them. No US ROM is needed for the PAL build, the converters or the game.

## 2. Web target: decisions (G1)

### 2.1 ABI: wasm64 C code lowered to wasm32 (`-sMEMORY64=2`) — the key decision
The Conker playbook says "target wasm32 first" because a 32-bit target matches the N64. Here that is
**wrong**: the PC port is LP64 throughout — hundreds of `#ifdef PORT` layout fixes, `uintptr_t`
arithmetic, 16-byte PC `Gfx`, and the sidecar converters emit LP64 struct layouts. A wasm32 (ILP32)
build would be a new, untested third ABI needing its own sidecars.

So the C is compiled as **wasm64** (LP64, same layouts as x86-64/aarch64 Linux) and Binaryen lowers the
module to **wasm32** (`-sMEMORY64=2`): it runs on every wasm engine (no memory64 support needed, Safari
included), and every load/store address is **wrapped to 32 bits**. That wrap is a feature: a
sign-extended s32-held pointer `0xffffffff8xxxxxxx` dereferences the right byte (verified in G1).

Costs/risks: pointer *comparisons* between a sign-extended and a zero-extended copy of the same address
still differ (D441 already fixed the known `(u32)`/`(s32)` truncation sites); the Emscripten JS glue in
this mode indexes heap arrays with `>>`, so **memory JS touches must stay below 2 GiB** (see 2.2).

### 2.2 Memory map (wasm linear memory, `INITIAL_MEMORY` 2112 MiB, no growth)

| Range | What | How |
|---|---|---|
| `0 .. 0x10000000` | unused null zone | `-sGLOBAL_BASE=256mb` |
| `0x10000000 .. 0x20000000` | **cart window**: ROM (12 MiB) + sidecars | `scripts/web/gen_cart_wasm.py` turns `romassets_e.s` into labels inside one 256 MiB `.rodata..ge_cart` section, linked **first**, so every label keeps its native value; zeros are packed out of the .wasm; `romdata.c` copies ROM + sidecars there and checks the address |
| `0x20000000 ..` | static data, stack, C heap | like the Linux build's `-Ttext-segment=0x20000000`, so fast3d's address classes (`seg_addr`) work unchanged; game zero-init globals are forced into `.data` |
| `0x80000000 .. +8 MiB` | **N64 DRAM, one view (V1 == K0)** | wasm cannot map pages twice; with `PORT_DRAM_V1_BASE = PORT_DRAM_K0_BASE = 0x80000000` both `off | 0x80000000` and fast3d's `w1 + K0` hit the bytes V1 pointers use. The s32 problem that made native use 0x70000000 disappears with the 32-bit wrap (D441 already ran all levels with the arena at 0x90000000). `dramReserve()` checks the heap break stays below |

wasm objects have **no absolute symbols** (clang's wasm assembler crashes on `.set sym, CONST`, wasm-ld
has no `--defsym`): hence the cart section, and `port/src/web/webdram.h` (force-included) turns the
three absolute DRAM symbols of `dram_syms.S` into dereferenced pointer variables (`cfb_16` →
`(*ge_web_cfb_16)`), which keeps the game's own declarations valid C; one use in a static initializer
gets a build-dir constant macro instead (`scripts/web/web_srcfix.py --abs`).

Risk: 2.06 GiB initial memory is fine on desktop Chrome (untouched pages cost nothing) but will not fit
32-bit/mobile browsers. Later option: move the arena lower and route the five `| 0x80000000` game sites
and fast3d's K0 mapping through one helper (needs a rule-2-style review), which would allow ~300 MiB.

### 2.3 Threads: cooperative fibers, the browser drives the retrace
Same as Conker. `port/src/web/webkernel.c`: each libultra thread is an `emscripten_fiber_t` (ASYNCIFY)
with static C + asyncify stacks (1 MiB each, fixed addresses), a priority scheduler runs from
`requestAnimationFrame`. `libultra.c` keeps its queue code: on the web its `pthread_cond_wait` points
become fiber blocks (every wait is inside a `while (!cond)` loop, so wake-ups are optimistic),
`pthread_cond_signal` wakes waiters and **preempts** when a higher-priority thread was waiting (libultra
`osSendMesg` semantics), the tick thread becomes `portWebRetrace()` called at **PAL 50 Hz** (20 ms fixed
step, at most 3 per animation frame, backlog dropped), timers are serviced there. Busy-waits
(`frametiming.c` polling `osGetCount`, NOBLOCK queue polls) park the thread until the next browser
frame after 64 consecutive polls. gfx tasks run inline (no render worker). A stall report prints who
waits on which queue if no thread ran for 120 frames.

Not pthreads: SharedArrayBuffer + COOP/COEP, GL from a worker, and nondeterministic preemption would all
work against online lockstep later. JSPI could replace ASYNCIFY later (smaller/faster), if Emscripten
fibers support it by then.

### 2.4 Compiler differences (clang/wasm-ld vs GCC), handled without editing game files
- `-fms-extensions` gives the `inherits` idiom what it needs in clang.
- libc++ wants its headers before any same-named C header; the port's libc shadows (`port/shim`) won
  for C++ TUs, so C++ sees the project include dirs as `-idirafter`.
- Build-dir copies (`scripts/web/web_srcfix.py`) for 4 game files: a clang bug with `#pragma weak A = B`
  after `extern A;` (lv.c, spectrum.c), the static-initializer DRAM symbol (initanitable.c), a function
  declared as data to take its address (initweaponanigroups.c).
- **Calls:** wasm traps on any call whose signature differs from the definition (Conker trap 3/4/14).
  The decomp has 27 such cross-TU calls (implicit/K&R declarations, `extern f32 f()` vs `int f()`,
  missing/extra args). `scripts/web/sigadapt.py` + `sigadapt.tsv`: the calling TU is redirected to a
  generated adapter that converts like a register ABI (i32→i64 zero-extend, truncate, missing args 0,
  extra dropped, numeric f32↔int). Rows marked FIDELITY need review: `bondinvGet*ForIndex` (8 watch-
  menu getters) return `int` but `options.c` reads `f32`; on MIPS/x86-64 the caller sees the inner float
  still in the FP return register, the adapter truncates it. `pc_protos.h` is enabled for wasm64 and
  completes 4 prototypes called inconsistently inside one TU (clang otherwise emits `_bitcast_invalid`
  traps). `scripts/web/build.sh` reports both counts; both must be 0. **Indirect calls** through
  mismatched function-pointer types also trap (seen once: `rmonMain(void)` as a thread entry); expect
  more (handler tables) → site-typed trampolines as in Conker if they multiply.
- The decomp's own `strtol`/`sprintf`/`acos`/`asin` replace libc's program-wide on native (exe symbol
  wins); on the web C TUs are redirected to the game's versions, libraries keep libc.
- The game-side 64-bit fixes gated on `__x86_64__` are enabled by defining it for game TUs only.

### 2.5 Graphics, audio, input, files, saves
- **GL:** SDL2 (Emscripten port) creates a WebGL2 context ("GL3.0es"); fast3d's existing ES path
  ("300 es" shaders) works unchanged: the 3D Nintendo and Rareware logos render (G1). glad
  reports missing desktop-only entry points (harmless; silence later). Framebuffer effects that read
  back (`copy_framebuffer`) need checking under WebGL.
- **Audio:** SDL2's Emscripten audio (ScriptProcessor, 22050 Hz) opens. Later: AudioWorklet ring,
  start on a user gesture, and the virtual `AI_LEN` for determinism (Conker trap 7).
- **Input:** SDL keyboard/mouse works through Emscripten; gamepads via SDL's Gamepad API backend.
  Pointer lock for mouse aim needs a click.
- **Files:** Emscripten MEMFS at `/data` (`$S/` resolves to `data/`). Saves/config: mount **IDBFS** on
  `/data/save` (or sync `ge007.eep`/`ge007.ini` to IndexedDB on write), with export/import in the page.
  **Done (G5):** sync on write (C notifies the page after each write; debounced IndexedDB copy per ROM
  SHA-1, flush on hide, localStorage copy on pagehide), export/import with a game-CRC check, `?nosave`,
  online sandbox `GESaves.sandbox()` (HANDOFF "Saves in the browser").
- **ROM:** page file picker → byte-order normalisation (z64/v64/n64) → SHA-1 must be the EU ROM →
  IndexedDB → MEMFS `/data/ge007.pal-final.z64` → `romdata.c` copies it into the cart window.

### 3.2 What must be produced in the browser, and how

**User decision (2026-10-29):** bulk media (logos, textures, fonts, audio) and game data tables (weapon
stats, model headers, skeletons, image tables, setup data) compiled into the binary are ROM data and must
come from the player's ROM in the browser (template + fill at boot, C sidecar converters run in wasm,
cached in IndexedDB). Small initialised constants inside the decompiled game C files count as code and may
stay. Deploy gate: scan the shipped wasm/js/site for ROM byte runs before every deploy. (Classes B, C, E
of 3.1 must go; class D: only the small constants stay — the W3 size audit draws the line per table.)

1. **Sidecars (E): port the three emitters to C** (`port/src/preprocess/` style, as in the PD port),
   run them in wasm at first launch on the player's ROM, cache the output in IndexedDB keyed by
   (ROM SHA-1, converter version), copy into the cart window. Their committed inputs: filelist/names
   (class A, fine) and the ModelFileHeader counts (read them from the game's compiled tables after 2.).
   Gate: byte-identical to the Python output for the EU ROM (dev check in the container).
2. **Bulk media (B) and data tables (C/D): "template + fill from ROM".** At build time (dev, with the
   ROM, in the container) a tool walks each such object's initializer (clang `-ast-dump=json`), keeps
   the *structure* (symbol references, pointers, sizes) and replaces every scalar leaf with zero in a
   generated template TU; it also emits a fill table: (object, LP64 field offset, width, ROM segment,
   N64 offset) — offsets only, committable. At boot the web build fills the scalars from the ROM's
   (decompressed) segment bytes with the right byte order. The ROM locations come from searching each
   object's N64 big-endian image (compile the same TU for a 32-bit BE target, or the decomp's map) in
   the EU ROM. Gate: the filled memory equals a dev build with the real initializers, byte for byte.
   `font_chardataj.c` is simply excluded from the EU web build.
3. **Release gate "no ROM bytes in the site":** a check that scans `ge007.wasm`/`.js` for any >= 64-byte
   run present in the EU ROM (raw and decompressed segments, both byte orders) and fails the deploy
   (`scripts/web/deploy_check.sh`; the threshold the user set is 64 bytes).
**Status (G4, 2026-10-30): 1.–3. landed** — details, numbers and the residual list in
`docs/web/ROMDATA.md`. 1: `port/src/convert/geconv.c`, byte-identical to the Python output, run in the
page before `main()`, IndexedDB cache. 2: done post-link instead of from the clang AST: the template is
the linked wasm with every ROM-matching run of the decomp/asset data zeroed (`tools_web/romfill.c`:
runs >= 16 B, display lists, anchored pieces incl. mixed-width fields; pointers never touched), the fill
table holds offsets only, the page fills before `main()` and checks CRCs; byte-identical memory proven
by an independent SHA-256 (`scripts/web/fillcheck.py` vs `&fillcheck`). Fonts / JP glyphs are not even
linked (unreferenced). 3: `scripts/web/romscan.sh` (>= 64 B, raw + RZ streams, both swaps) inside
`scripts/web/deploy_check.sh`: 178 runs / 58 KB before, 4 allowlisted third-party runs after. Left:
~67 KB of short strings in the merged string pool (mostly non-game) and ~5.7 KB of small fields in a
few game tables whose PC layout differs (struct-aware fill = next step). `?assets=` stays a dev-only
override; a stripped build needs the dev ROM at build time.

## 5. Main risks
1. **Asset scrubbing (W3)** is the largest unknown: how many data tables there are and how many contain
   pointers/compressed data. Mitigation: automated template + fill with a byte-exact gate.
2. **Call-signature traps** beyond the 27 known: indirect calls through handler tables only show at run
   time. Mitigation: log every trap; trampolines with a signature check (Conker `icall.py` design).
3. **Cooperative scheduling vs real preemption**: the native port relies on preemptive threads in a few
   places (audio manager vs game thread, D147/D152 interrupt-mask lock); a busy-wait on a flag set by
   another thread hangs a fiber. The W1 stall is likely this class.
4. **2 GiB memory** layout (2.2): desktop only; a lower arena needs the K0 helper.
5. **ASYNCIFY overhead** (size/speed) with a software RSP: measure; JSPI later.
6. **Fidelity** of adapter rows marked FIDELITY and of wasm float semantics vs x86-64 (should be equal;
   NaN payloads differ only in theory).
7. Upstream drift: we track `jkdansereau/goldeneye-pc-port` `main`; merges must keep the web guards.
